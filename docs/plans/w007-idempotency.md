# W-007 plan: Idempotency-Key store with replay

Critical seam (idempotency, migration, a filter in front of `ApiControllerBase` actions): plan first, cross-family review after. Revision 2 folds in the Codex plan review (`docs/reviews/codex/2026-11-27-w007-idempotency-plan.md`). Decision: D-050, promoted to ADR-013.

## Goal
A client that retries `POST /api/v1/customers` or `POST /api/v1/webhooks/subscriptions` with the same `Idempotency-Key` gets the first response back (same status, body, `Location`, `ETag`) instead of a second row or a 409, and a client that reuses a key for a different request is told so. Shape follows the IETF `Idempotency-Key` header draft (draft-ietf-httpapi-idempotency-key-header).

## Decisions (revision 2, after the Codex plan review: 5 HIGH, 8 MEDIUM, 1 LOW, verdict REVISE)
| Id | Decision |
|---|---|
| A | Opt-in per action with `[Idempotent]`, implemented as an MVC **resource filter** (`IAsyncResourceFilter`), applied to the two create POSTs only. A resource filter runs after authorization filters and BEFORE model binding (so it can buffer and rewind the body), and its `next()` returns AFTER the result has executed (so `Location`, `ETag`, `Content-Type` and the serialized body exist). An action filter cannot do either (review #3). |
| B | Header syntax: one Structured Field String per draft-ietf-httpapi-idempotency-key-header-09 §2.1 (`Idempotency-Key: "abc"`, `\"` and `\\` escapes), decoded length 1-255. A bare token matching `[A-Za-z0-9._:-]{1,255}` is also accepted for curl convenience (documented deviation). Two header lines, a comma list, bad quoting or anything else -> 400 `idempotency.key_invalid`. Absent -> today's behaviour. `ApiControllerBase.IdempotencyKey` is not used by the filter (review #8). |
| C | Scope = (authenticated user id, `METHOD + route template`, decoded key). Fingerprint = SHA-256 of the raw body, buffered up to `MaxRequestBytes` (default 64 KiB; larger -> 413 `idempotency.body_too_large`). Same scope + different fingerprint -> 422 `idempotency.key_reused`. |
| D | Claim before execute, atomically, in its own committed statement through `SqlExecutor`: `INSERT ... ON CONFLICT (actor_id, endpoint, key) DO UPDATE SET <every column reset, new claim_token> WHERE idempotency_keys.expires_at < now() RETURNING claim_token`. A returned token = this request owns the key. No row returned = read the existing row: `completed` + same fingerprint -> replay; `pending` younger than `InProgressSeconds` (default 60) -> 409 `idempotency.in_progress` + `Retry-After: 1`; `pending` older -> 409 `idempotency.outcome_unknown` (no Retry-After; the problem detail says to check whether the resource exists and use a new key). **A claimed key is never reclaimed** (review #1, #5): an ambiguous outcome never re-executes, so the worst case is a stuck key until expiry, never a duplicate. |
| E | After the result executed: 2xx -> `UPDATE ... SET status='completed', response... WHERE id=@id AND claim_token=@token` (fenced). A 4xx produced by a `FugueError` (nothing was committed in this architecture: a failed command does not commit) -> `DELETE ... WHERE id=@id AND claim_token=@token`, freeing the key for a corrected retry. 5xx, an exception, a client abort, a response over `MaxResponseBytes` (default 256 KiB) or a failure while storing -> the row stays `pending` (outcome unknown; review #2). |
| F | Replay writes the stored status, the allowlisted headers (`Location`, `ETag`, `Content-Type`; values checked for control characters before storing and before sending) and the body, plus `Idempotent-Replayed: true`. Correlation, saga and CORS headers are generated per request as usual. The handler, audit and outbox do not run again. Every response of an `[Idempotent]` action that carries a secret (webhook create) and every replay sends `Cache-Control: no-store` (review #10). |
| G | Stored bodies are encrypted with Data Protection (purpose `Fugue.Idempotency.v1`). Threat boundary (review #9): the key ring is stored UNENCRYPTED in the same database (`DatabaseXmlRepository`), so this protects against a leak of the table, a log or a partial export, not a full database dump; production should wrap the key ring (X.509 / KMS), recorded in `docs/archive/deferred.md`. If a stored body cannot be unprotected, the replay answers 500 `idempotency.replay_unavailable` and the key is NOT freed. |
| H | Table `idempotency_keys`: `id` uuid pk, `actor_id`, `endpoint`, `key`, `request_hash` bytea, `claim_token` uuid, `status` CHECK (`pending`,`completed`), `response_status` int null, `response_headers` jsonb null, `response_body` bytea null, `expires_at`, plus the `IAuditable` stamp columns (as the Data Protection key entity does), with `[NoAudit]` so the audit interceptor skips it (review #6, #7). UNIQUE (actor_id, endpoint, key); index on `expires_at`. No baseline is widened. |
| I | Retention: `expires_at = now + RetentionHours` (default 24). Purge: a hosted service every `PurgeIntervalMinutes` (default 60) runs `DELETE ... WHERE expires_at < now()` in batches of `PurgeBatchSize` (default 500); a replaced row has a fresh `expires_at`, so the predicate is the only fence needed. Options `Idempotency:` validated at start. |
| J | Accepted limits: (1) a stuck `outcome_unknown` key until expiry after a crash between commit and completion; (2) replay is not re-authorized beyond the endpoint permission, which the filter re-checks on every request because it runs after authorization: a replay discloses only the response the same user already received (review #4, judged LOW); (3) no per-actor rate limit on the creates (deferred). |
| K | Contract (review #12): shared problem components for 409 (`idempotency.in_progress`, `idempotency.outcome_unknown`, merged with customer create's `customer.email_taken`) and 422 (`idempotency.key_reused`) in `FugueDocumentFilter`; the optional `Idempotency-Key` header parameter, `Retry-After` on the 409 and `Idempotent-Replayed` on 201 via `FugueOperationFilter`; `Idempotent-Replayed` added to CORS exposed headers; snapshot refreshed; console client regenerated; the console sends a quoted fresh key per create submission and reuses it on that submission's retries. |

## Slices (commits, each green)
1. Schema: entity + id, EF mapping, migration, catalog row, schema pin test.
2. Store + filter + options + purge; tests (review #13): exact replay (status, body, Location, ETag, Content-Type) with ONE business row, ONE audit row and ONE outbox event; different body -> 422; concurrent same key -> one execution; a 400/409 frees the key; a 5xx/exception leaves it pending and a later retry gets `outcome_unknown`; a stale completion with the wrong claim token changes nothing; expired key is replaced and re-executes; other user same key is independent; malformed, quoted, escaped, repeated and list headers; unsafe stored header refused; corrupt ciphertext -> 500 and key kept; replay after a new host instance (key ring reload) decrypts; stored webhook body does not contain the secret; no header unchanged; claim/complete/purge write no audit rows.
3. Contract: operation filter, snapshot, Bruno request(s), runbook section, console key header + regenerated client.

## Out of scope
Idempotency on PUT/DELETE (If-Match already makes them safe), on state-transition POSTs (suspend/reactivate/rotate-secret carry If-Match; redeliver is naturally idempotent: it only re-queues a dead delivery and answers 409 otherwise), a distributed lock, response streaming.
