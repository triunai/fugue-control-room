1. **HIGH — Concurrent permission changes can disappear from `audit_log`.** [AuditLogSaveChangesInterceptor.cs:82](src/Fugue.Infrastructure/Audit/AuditLogSaveChangesInterceptor.cs:82)  
   `OverrideAdmin` deliberately forces writes even when submitted values equal its loaded snapshot. If request A reads “allowed,” request B commits “denied,” then A writes “allowed,” this interceptor discards A’s equal original/current values and skips its audit row entirely. The permission changes without a general audit record. **Fix:** concurrency-check or lock override updates so originals reflect the overwritten database state; audit every column actually written.

2. **MED — Retrying a failed EF save commits duplicate and phantom successes.** [AuditLogSaveChangesInterceptor.cs:58](src/Fugue.Infrastructure/Audit/AuditLogSaveChangesInterceptor.cs:58)  
   Generated audit entities remain `Added` after `SaveChanges` fails. For example, add two customers with duplicate emails, fail the save, detach the conflicting customer, then retry. The retry adds another audit entity for the retained customer and persists the previous audit entities—including a success for the detached customer that never existed. **Fix:** track audit entities created for each save attempt and detach them on failure or cancellation; add a same-context retry regression test.

3. **MED — Failure rows join the transaction they are supposed to survive.** [AuditTrail.cs:42](src/Fugue.Infrastructure/Audit/AuditTrail.cs:42)  
   `RecordFailureAsync` uses the same `SqlExecutor` as successful writes, which enlists in `CurrentTransaction`. Begin an outer `IUnitOfWork`, dispatch a failing command, then roll back: its failure row disappears too. A duplicate Dapper insert inside that unit of work leaves PostgreSQL’s transaction aborted, so the failure insert itself fails and is swallowed by `AuditBehavior`. **Fix:** persist failures through a separate connection/transaction, after business rollback where possible, with a bounded independent cancellation policy.

4. **MED — Seeder overwrites lose row identity and before/after evidence.** [CustomerSeeder.cs:50](src/Fugue.Infrastructure/Persistence/Seeding/CustomerSeeder.cs:50)  
   Edit a seeded customer, then rerun seeding. The upsert overwrites its name, email, phone and status, but records only an empty-change summary with `EntityId = null`. Neither an entity-filtered audit query nor the summary reveals what was overwritten. **Fix:** capture each affected row’s old/new values and ID within the transaction; skip unchanged upserts to control volume.
