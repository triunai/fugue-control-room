Fugue, explained

A claims platform for motor and property claims across six APAC markets. Claimants report an incident, follow their claim and answer questions. Claims officers pick up, assess and decide. Managers see workload and outstanding liability, per currency. One API, one Angular app for everyone.

The brief, answered

Every ask, and where it lives

The brief names three groups and what each must be able to do. Each row below is a screen you can open and an API route with tests behind it.

Service boundaries

One deployable; the transaction is the boundary

A claim's new state, its timeline row, its audit row and its outbox event must commit together or not at all. Inside one process that is one database transaction, so claims stay one module in one deployable. Anything that only reacts to a claim (notifications, payments, finance reporting) gets events and can become its own service without a distributed transaction.

The contract between the app and the API is owned by the backend: the OpenAPI document is generated from the controllers, pinned by a committed snapshot that a test regenerates, and the Angular client is generated from it.

The claim

A guarded state machine

A claim has a number the claimant quotes (CLM-SG-2026-000001), a market whose currency is fixed (SG SGD, MY MYR, TH THB, HK HKD, ID IDR, PH PHP), a line (Motor or Property), the claimant, the assigned officer, the incident, and money in minor units. Every move is a method on the claim that returns a result; an illegal move changes nothing and answers 409.

stateDiagram-v2
    [*] --> Submitted: submit (claimant)
    Submitted --> UnderReview: pick up (officer)
    UnderReview --> InfoRequested: request info
    InfoRequested --> UnderReview: answer (claimant)
    UnderReview --> Approved: approve (needs a reserve)
    UnderReview --> Rejected: reject (with a reason)
    Approved --> Settled: settle (manager)
    Rejected --> [*]
    Settled --> [*]

Approving needs a reserve and an amount with 0 < amount ≤ reserve. Policy, party and payment are references, not tables: the policy system owns cover, and payment belongs to the settlement consumer.

Who sees what

A claimant sees their own claims, and nothing else

Every read and every command loads the claim through one scope filter. A claim outside your scope answers 404, exactly like a claim that does not exist, so ids reveal nothing. The reserve (the insurer's internal estimate) and the officer's name never reach the claimant; staff actions read as "Claims team".

All use the development-only password Fugue-Dev-Passw0rd!. Authorization is enforced once, at the HTTP edge ([HasPermission] on every action, pinned by an architecture test); permissions are read fresh on every request, so a revoked role takes effect on the next call.

Edits that collide

Two officers act on the same claim

Every claim row has a version (Postgres xmin), sent as the ETag. Every action after submit must send it back as If-Match. Missing is 428; stale is 412, checked before the state machine runs, so the slower officer is told to reload instead of getting a business error about a state they never saw.

Duplicate submits

Press "Submit" twice, get one claim

A claimant on a bad connection cannot know whether a submit worked. Submit requires an Idempotency-Key: a retry with the same key replays the first answer instead of filing a second claim, and the same key with a different body is refused. A duplicate claim is real harm, so on this route the key is required, not optional.

flowchart TB
  REQ["POST /claims · Idempotency-Key: k1"] --> CL{Key k1 for this user}

  OK -->|"no (4xx)"| FREE[Free the key] --> ERR[4xx]

  CL -->|done, different body| U422[422 key reused]
  CL -->|no key| U400[400 idempotency.key_required]
REST or Kafka

Commands are REST; every state change is also an event

A claimant submitting or an officer approving needs the answer now: accepted, 409 with the reason, or 412 because someone else got there first. REST gives that verdict in the same round trip. Everything other systems need to know leaves as an event through the transactional outbox, so no event is lost and none is sent for a change that rolled back.

OperationHowWhy
Submit, pick up, reserve, ask, answer, decide, settleREST commandThe caller needs the guard's verdict now (201/200, 409, 412, 428, 400).
Queue, claim record, timeline, counts, workload, exposureREST queryRead your own write; keyset paging; as fresh as the last commit.
claim.*.v1 eventsOutbox, async, at least onceNotify the claimant, project exposure, pay, score fraud; none of these may fail or slow the claim.
Partner or telematics intake at volume (not built)Kafka in front of the same commandNobody waits for a human answer; a consumer validates and calls the command behind its own authorizer.

Signed webhooks (default)

A background dispatcher sends each event as a POST signed with HMAC-SHA256, retries with backoff and jitter, and dead-letters after its budget. Receivers dedupe on the event id.

Kafka (optional, off by default)

The same outbox can also publish to Kafka: one topic per event family, key = claim id so each claim's events stay in order, idempotent producer with acks=all, and the relay marks an event sent only after the broker acknowledges it.

Workload and exposure

Outstanding liability, never summed across currencies

Exposure is reported per market, line and currency: the outstanding reserve on open claims and the approved amount not yet paid. There is no grand total, because adding SGD to IDR is meaningless without a rate and a rate date, and choosing those is a finance decision. Money is a bigint of minor units plus the ISO currency code, never a float.

ReportAnswers
Workload (GET /claims/workload)Per officer: open claims by status, the oldest open one, decisions in the last 7 and 30 days, median days from submit to decision; unassigned claims; open claims in age bands 0-2, 3-7, 8-14, 15+ days.
Exposure (GET /claims/exposure)Per market, line and currency: open count, outstanding reserve, approved not settled, open claims without a reserve (they cannot count toward exposure until an officer sets one). Each cell opens the matching claims in the queue.

Both are plain SQL over live rows, refreshed every 15 seconds in the console and whenever the window regains focus. At scale they become projections fed by the claim events the outbox already emits.

Layers and slices

Onion rules, organised by feature

Four projects, dependencies pointing inward only: the domain knows nothing about the web or the database, and the application layer never references ASP.NET Core. Inside that, each use case is one file holding its command, validator and handler. Controllers are one line per action. Architecture tests fail the build if any of this is broken.

Written once, applied to every slice

Logging, audit and validation run as mediator pipeline behaviors; correlation ids, auth, module switches and rate limits as middleware. A new feature cannot forget them.

Reads and writes

EF Core for reads (no tracking, keyset paging) and version-checked updates; Dapper for inserts and set-based SQL, always inside EF's own transaction.

Errors

Typed failures, one shape on the wire

Handlers never throw for expected problems. They return a typed failure with a stable code; one table maps the type to an HTTP status, and every error leaves as RFC 9457 application/problem+json with the correlation id in it.

Audit

Three records, three audiences

The claimant reads the timeline. Staff and admins read the audit log: who changed which field from what to what, under which correlation id. Other systems read events. All three are written in the same transaction as the change, and both the timeline and the audit log refuse UPDATE, DELETE and TRUNCATE at the database.

Audit log

Field-level diffs, never sampled, sensitive fields masked; a failed command leaves one failure row. Searchable in the console (Meilisearch, fed from the append-only log; the plain filtered log still works if search is down).

Access and grant audit

Sign-ins, refreshes, 401s (capped per IP), 403s and switched-off modules; every role, group and override change.

The console

One Angular app for every persona

Each persona lands on the page that answers "what should I do now". The claim record puts the two tracks on top, a next-step card that names what blocks a decision, and one primary action. Screens refetch every 15 seconds and on focus, paused while a form is open, so the claim and its ETag do not change under a half-filled form.

Under the hood

A side panel on every page shows its live API calls (status, timing, If-Match, ETag, Idempotency-Key), how the API handles that screen, each guard with the backend code that enforces it, the tests that cover it, and the ADRs behind it.

Spreadsheet bridge

A reserve sheet and a claim assessment worksheet for staff who work in spreadsheets, both with Open in Excel. Saving goes through the same guarded API commands, one per row.

Tests

The invariants the code cannot argue with

Most of the code was written by AI agents, so the tests are the specification they must satisfy. Each one pins a rule of the domain, such as "a stale ETag is 412 and nothing is written", "outside your scope is 404, never 403", or "exposure is never summed across currencies". They are deterministic on purpose: a real database instead of mocks of it, time-dependent rules on a fake clock. A red test means the code drifted, and the git hooks run them before every push.

Built with AI

Directed, challenged, and checked by machines

A lead agent planned and split the work into parallel lanes, each in its own git worktree; every lane was merged only after its gates passed again on the combined code. Reviews came from a different model family, and an independent reviewer judged the product against the brief. The working journal records what was asked, what the AI proposed, and what was accepted, challenged or overridden.

Gates that do not depend on trust

Commit: secrets scan, formatting. Commit message: conventional commits, a decision or thread reference. Push: build and the full test suite. A command guard blocks force pushes and skipped hooks.

Where to read it

docs/ai-journal.md (the journal), docs/decisions.md and docs/adr/ (why), docs/failure-modes.md (traps hit and their fixes), docs/reviews/ (the independent reviews).
